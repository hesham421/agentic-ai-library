# aias — Request Verification Service (backend)

This is the **backend** repository of project `aias`, the Request Verification
Service: a standalone Spring Boot service that verifies a government service
request before an employee approves it — it runs the service's configured
read-only queries, fetches and reads the attached documents, compares them with
the service's conditions, and stores an evidence-backed compliance report. The
employee stays the decision maker. This repo contains the Java source code, the
Maven build, the AI skills and commands, and the backend tooling.

> **Governance does NOT live in this repository's own tree.**
> Every governance artifact (profile facts, SRS, contracts, execution plans,
> delivered packages, API documents) lives in the aias governance project,
> mounted here as the submodule `governance/shared/` and read through
> `scripts/gov-module.py`. The AI skills live in `.claude/skills/` so they
> auto-load via the Skill tool; the slash commands live in `.claude/commands/`.
> See "Workspace Layout" and "Where to Find Governance" below.

## Project Facts (from the aias profile — do not contradict)

| Area | Fact |
|---|---|
| Stack | Java 21, Spring Boot 4, Spring AI 2.0 — the engine uses the provider-neutral `ChatModel` / `Prompt` / `ChatOptions` API only, no provider-specific feature (G12, AIAS-9). `pom.xml` currently pins `java.version` 25 and an enforcer rule `[25,)`; the profile says Java 21 — write Java 21-compatible code |
| Modules | `REG` Service Registry · `DOC` Document Access · `CHK` Check Engine · `RPT` Report Store · `INT` Host Integration — built in waves REG → DOC → CHK → RPT → INT (`gov-module.py --track backend modules`) |
| Deployable | ONE deployable. Modules reach each other in-process through the published contract interfaces (`platform/contracts/contract-<mod>.md`), never over HTTP and never through another module's repository or entity |
| Layers | controller, service, domain, port, adapter, repository. Domain behaviour lives in domain classes; every external dependency (host query channel, document source, model) is a port with a replaceable adapter. No workflow engine — the check pipeline is fixed code |
| Backend phases | CORE → DATA-DOM → PORTS → SVC-API → ALIGN-BE → CROSS-MOD (integration, last). There is no security phase, no separate doc phase and no separate integration-contract / integration-runtime phase |
| Test units | `RULE-SCENARIOS`, `API-SCENARIOS`, `MODEL-EVAL` (the fixed known-result request set run on every model change), plus `INT-XM` (integration) |
| Database | The service's OWN schema on Oracle 19c. Identity PKs `NUMBER(19) GENERATED BY DEFAULT AS IDENTITY`, PK property pattern `{entity}Id`, audit fields `createdAt` / `updatedAt` (transactional entities), booleans `NUMBER(1)`. **Hard delete** — no soft delete, no active/inactive flag. Host identifiers (request number, employee identity) are stored as strings exactly as the host sent them and are never foreign keys |
| API | Base `/api/v1/{resource}`; `POST` = create (start a check, upload documents, record a decision), `GET` = read; no update or delete is exposed. Responses are plain JSON objects/arrays (no envelope). Errors are RFC 9457 `ProblemDetail` → `{type, title, status, detail, code}`, `code` = `{MOD}-{http}[-{SLUG}]` (e.g. `CHK-404-CHECK-NOT-FOUND`). Statuses: 200, 201, 202, 400, 401, 403, 404, 409, 413, 415, 422, 500, 502, 504 |
| Security | **None in this version.** No caller authentication, no permission model, no method-level authorization annotations, no permission codes or page registry — deferred by amendment A2 (domain-profile D7). The §12 guardrails below are NOT deferred |
| Languages | Messages in English; Arabic texts are `PENDING` (per-module ADR) |
| Guardrails (raw idea §12, G1–G14) | The LLM analyses only: it never writes SQL, is given no tool that runs SQL, and never triggers approval (approval runs only from the employee-decision operation, where the service enables it). Host data is read only through a read-only user (MCP query channel; BLOBs over read-only JDBC). Query parameters are bound or strictly type-validated. File paths are validated inside the storage root before opening. Nothing that could not be read is skipped silently — a missing or unreadable required document prevents `COMPLIANT`. Document content is data, never instructions. Per-check limits: `aias.check.timeout=PT2M`, `aias.check.max-rows=100`, `aias.check.max-file-size=10MB`, `aias.check.max-uploads=20` — platform configuration, never read from a service definition. No state is carried from one check to another |

## Where to Find Governance

This repository holds **no governance artifacts**. It knows two things: where
to read them, and where it may write. Both are the same place — the project
repository the governance factory publishes, mounted here as a submodule at
`governance/shared/` (branch `master`).

`git submodule update --init --recursive` after a clone, or none of the paths
below exist.

> **One tool reads the contract — never type a path.** `scripts/gov-module.py`
> reads every path and vocabulary from what the factory publishes
> (`governance/shared/platform/profile-summary.json → consumer`, schema 7, and
> `platform/modules-registry.json`). Every command and skill calls it:
> ```bash
> python3 scripts/gov-module.py --track backend pin                 # 0 = schema 7 · 3 = the project predates v7 (the factory owner runs gov.py upgrade-project) · 1 = refused

### The review gate

The factory runs ONE review gate per module, `analysis` (after P4), and splits

### The feedback contract — record it, do not patch it

The plan is the factory's to write. What you discover while implementing goes
into **this repo's own partition** through `gov-module.py record`, and the
factory reads it (`gov.py feedback`) and answers it (`gov.py answer-feedback`).
Every command below is `python3 scripts/gov-module.py --track backend …`.

| Row | Command | When |
|---|---|---|
| `package_results` | `record MOD package UNIT --passed N --failed N` | after building/testing each unit — accepted when its listed tests are green (`tests-green`); a `no_tests` unit records `0/0` after a clean build |
| `features_done` | `record MOD feature FEAT-MOD-NNN` | after executing a feature prompt (`plan.features`) |
| `api_verify` | `record MOD api_verify --version <delivered_version> --result PASS\|FAIL` | after api-verify; the frontend's delivery stays OPEN until it is PASS |
| `api_doc_gaps` (key `endpoint`) | `record MOD api_doc_gaps --key "<METHOD> <path>" --resolution "OPEN — …" [--detail …]` | the plan / API document is wrong or silent |
| `blocked` (key `id`) | `record MOD blocked --key OQ-… --resolution "OPEN — …"` | an OQ or decision blocks a task |
| `deferred_xm` (key `id`) | `record MOD deferred_xm --key XM-… --resolution "DEFERRED — <requires> not met"` | an integration package whose `requires` is not met |

A `resolution` must **start with a declared word** — OPEN / DEFERRED / PENDING
(the factory owes an answer) · RESOLVED / CLOSED / IMPLEMENTED (settled in code)
· HUMAN / ADR (needs a decision). The tool refuses anything else ("blocked
pending …" is not a resolution); re-recording the same key replaces the row,
which is how a gap is closed. `xm_events` is the factory's channel — never
written here.

## Phase Execution Protocol

> Applies when executing a module's delivered packages. This section governs
> HOW to execute — the skill routing table above governs WHAT to use.
> `/orchestrate-module` is the full protocol; this is its summary. Every
> `gov-module.py` call below is `python3 scripts/gov-module.py --track backend …`.

### Entry
1. `./scripts/governance pull` (with `GOV_TRACK=backend`), `gov-module.py --track backend pin` (exit 3 → stop: the factory owner runs `gov.py upgrade-project`).
2. `gov-module.py --track backend plan [MODULE] --json` and `state-init [MODULE]`.
3. `gov-module.py --track backend delivery [MODULE]` — the first unit not `accepted` is where work resumes.

### Order
1. The exec phases in `plan.phases` order — for aias CORE → DATA-DOM → PORTS →
   SVC-API → ALIGN-BE — skipping the phase with `integration: true` (CROSS-MOD);
   a phase's units are its `exec_units` (each a `{unit}.package.json` +
   `{unit}.md`). Read the order from `plan`, never from this list.
2. Each XM edge is ONE integration package (`plan.integration`, the CROSS-MOD
   phase): built only when `requires_met`, otherwise recorded as `deferred_xm`.
   Integration packages are excluded from the module's own delivery.
3. Feature prompts not `done` (`plan.features`), then `record … feature`.
4. Test units (RULE-SCENARIOS, API-SCENARIOS, MODEL-EVAL; INT-XM with the
   integration packages), api-docs publication, api-verify → the `api_verify` row.

### Per unit
1. Read the unit's `.md` completely, its phase `*-HEADER.md`, `_SECTIONS.md`, the
   named blocks it cites, its operations in the API document (`plan.api_spec`),
   the db-script's `sql` fence / `dbf-matrix`.
2. Map each task to the skill routing table; read the skills from `.claude/skills/`.
3. Execute all tasks in order; write and run the unit's acceptance tests (its manifest's `tests`).
4. Run `gov-enforce-backend-contract` and `gov-enforce-library-contract` on the change.
5. `gov-module.py --track backend record [MODULE] package [UNIT] --passed N --failed N`.

### Blocked items — OQ / XM deferred
- OQ-blocked task → skip, mark in code `// TODO: OQ-[ID] — pending resolution`,
  `record [MODULE] blocked --key OQ-[ID] --resolution "OPEN — …"`.
- Integration package not met → `record [MODULE] deferred_xm --key XM-… --resolution "DEFERRED — <requires> not met"`.
- Continue remaining tasks — never stop the phase for a blocked item.

### Exit
`gov-module.py --track backend validate [MODULE]`, then `./scripts/governance push`.
Print units accepted / failing, blocked, deferred XM, gaps, next unit — and wait
for the user before the next phase.

### Constraints (NON-NEGOTIABLE)

- NEVER skip a unit within a phase
- NEVER invent field or column names — the db-script's `dbf-matrix` block and `sql` fence are ground truth
- NEVER invent an endpoint, status or error code — the API document is the contract
- NEVER copy QRC entries as production code — read intent, write implementation
- NEVER implement a blocked OQ item — mark and skip only
- NEVER add caller authentication, a permission model or authorization annotations — deferred by amendment A2
- NEVER weaken a §12 guardrail (G1–G14) to make a test pass
- NEVER hand-edit `execution-state.json` — `gov-module.py record` only
- NEVER advance to next phase without explicit instruction from user

## Running Locally

**JDK.** The profile targets Java 21; `pom.xml` currently pins `java.version` 25
and a `maven-enforcer-plugin` rule fails the build at `validate` under any JDK
older than 25. Until `pom.xml` is aligned, point `JAVA_HOME` at a JDK 25 to
build, and keep the code Java 21-compatible.

```bash
mvn -q -DskipTests compile    # build
mvn -q test                   # tests
mvn spring-boot:run           # run the one deployable
```

The service's own Oracle 19c schema, the host's read-only MCP query channel and
the model provider are configured through `aias.*` properties that the CORE
units define — environment settings, never committed values. While a free-tier
model provider is in use, send it only synthetic or anonymised requests and
documents (G13).

## Database Schema Policy

The service owns one Oracle 19c schema (runs, findings, documents, registry
data); the host data is never part of it and is reached read-only through the
query port.

- **Ground truth**: each module's db-script (`analysis/modules/<MOD>/P2/db-script-<mod>.md`,
  as of the delivered version) — its one ```` ```sql ```` fence is the DDL, its
  `dbf-matrix` block the column ↔ property map. Table names carry the module
  prefix (e.g. `REG_SVC_PKG`); constraint names (`PK_`, `UQ_`, `FK_`, `CHK_`)
  are taken verbatim from the DDL.
- **No migration tool is decided yet.** None is on the classpath and no
  delivered package names one. Do not add Flyway, Liquibase or
  `spring.jpa.hibernate.ddl-auto=update` on your own: adopting one is a decision
  for the user (record it with `gov-module.py --track backend record MOD blocked
  --key … --resolution "HUMAN — …"` if a unit cannot proceed without it). Once a
  tool is adopted, the usual rules apply: applied scripts are immutable, fixes go
  forward, one logical change per script, and the version number is derived from
  the directory at creation time — never written into a document.
- **Hard delete.** Rows leave only by the operations the plans define (e.g. the
  RPT retention purge, DOC's per-check upload cleanup). No soft delete, no
  active/inactive flag.

### If you are about to do X, the answer is always Y

- **About to add a backend execution step, a JUnit scenario, or a generated `execute-backend*.md` command?** → this repo (`src/test/java`, `.claude/commands/[MODULE]/`). Never `governance/shared/`.
- **About to change a plan, a package, an SRS, a contract or the API document?** → You can't from here. Record the problem with `gov-module.py --track backend record MOD api_doc_gaps …` (or `blocked`); the factory answers it.
- **About to add frontend work?** → Not in this repo. The aias frontend is its own repository.
- **About to edit `governance-tools/*.py`?** → Backend-only; edit it in `governance/governance-tools/`.
- **About to edit `.claude/commands/generate-module-setup.md` or a generated `[MODULE]/execute-backend*.md`?** → this repo's `.claude/commands/`.
- **About to write a report, investigation note, or audit writeup?** → `governance/project-artifacts/`. Never the root of `governance/`, never inside `governance/shared/`.
- **About to run TestSprite?** → Don't: it is not part of aias. API verification is the `api-verify` skill (the published api-docs held to the API document), recorded with `gov-module.py --track backend record MOD api_verify`.
- **About to add authentication, roles or permission checks?** → Don't: caller authentication is deferred to a later version by amendment A2; the owner adds it then.
- **About to edit `execution-state.json`?** → Only through `python3 scripts/gov-module.py --track backend record` (and `state-init`). A hand edit is how a resolution word the factory cannot read gets in.
- **About to edit `scripts/gov-module.py` or anything under `governance/shared/`?** → Don't. The first is the factory's verbatim copy; the second is the factory's output, published from the governance project.

### No new top-level content categories without explicit confirmation

Do not create a new folder type, a new cross-repo dependency, or a new
"shared" location without first producing a short written justification and
getting explicit human confirmation. Never skip straight to implementation.
Every repo reads only paths inside itself; anything two repos must agree on is
written into the governance project by the factory and read through the
submodule.

### Decision authority

This structure keeps this backend repo workable on its own, with the governance
project as its only external input. Any deviation — new duplication, new
cross-repo path reference, new shared location — requires evidence-based
analysis, a dry-run plan, and explicit human confirmation. Silent structural
drift is treated as a governance violation, not a convenience.
